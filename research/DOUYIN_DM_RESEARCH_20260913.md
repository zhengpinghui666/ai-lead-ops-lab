# 抖音私信限制与 Mimo 电竞引流方案

## 1. 核心结论

ClubOps 的目标是及时识别无畏契约玩家的陪玩需求，以简短沟通引导至 Mimo电竞公众号，随后交由俱乐部客服承接。需求包括明确询价、下单，也包括在正确上下文中可能接受付费陪玩的求带或找搭子。系统需要兼顾有效触达、平台可用性和真实效果，不能把发送数量当作最终成果。

**目前没有足够证据支持一套“避开这些词就能保证私信正常”的方案。** 在本次可核验的官方资料中，未找到面向当前个人账号、完整公开的私信禁词表或统一安全发送额度。官方用户协议涉及商业招揽、过度营销、刻意组合字符规避审核，以及未经许可的自动化访问和数据使用；这些要求覆盖内容和行为，不只是词面匹配。[^1]

**建议采用可解释的发送前检查，并把平台反馈与转化反馈分别处理。** 内容检查负责发现夸大承诺、错误身份、无关推销、联系方式和站外引导等需要审视的内容；账号与会话检查负责确认实际权限；发送记录负责区分平台接受、结果未知和收到回复。预检通过只表示符合项目当前规则，不能命名为“抖音审核通过”。

当前固定开场“点陪🥣看我主业”的转化反馈为零。可以提出三个待验证的解释：没有说清楚为何联系此人、没有体现他所表达的需求、跳转任务不够明确。但没有送达、阅读和完整回复数据，就不能把零转化单独归因于敏感词，也不能证明只换一句话就能解决。

| 决策 | 建议 | 当前证据边界 |
| --- | --- | --- |
| 词库 | 建立带来源、适用场景和版本的本地规则 | 通用词库不代表平台实际审核标准 |
| 开场 | 联系缘由、真实服务、一个明确动作 | 新文案均为讨论样例，未做真实转化验证 |
| 引导 | 优先核实当前账号可用、可审核的经营入口 | 不能假定个人简介、私信和企业组件规则相同 |
| 自动化 | 需求判断与发送权限分别检查 | 能技术调用不等于具备平台授权 |
| 结果 | 分层记录发送、回复、表达兴趣和转化 | 公众号后台不可取得时，转化保持未知 |

改进顺序应先让系统说清“联系谁、为什么联系、发送结果是什么”，再比较话术。不得以大量随机发送来寻找所谓安全阈值，也不应通过换号或变形文字继续触达已经明确拒绝的人。

## 2. 官方能力与资料适用范围

同一平台存在个人私信、企业经营私信、小程序主动授权私信等不同产品。查到接口、额度或经营组件后，必须同时核对账号主体、权限、接收方关系和具体入口。将一种产品的数字写成另一种产品的上限，会使系统在看似有规则的情况下继续失败。

| 资料 | 能证明什么 | 不能据此推导什么 |
| --- | --- | --- |
| 用户服务协议 | 平台对内容及自动化访问有约束 | 某词在所有普通私信中必定被封 |
| 隐私政策 | 用户可控制谁能私信，并设置屏蔽词 | 发送失败必定由营销文案导致 |
| enterprise.im 事件列表 | 特定私信事件需要企业号及对应权限 | 当前个人账号可任意给采集名单发消息 |
| 线索能力开放 | 存在需申请和经营者授权的经营私信能力 | 取得一个数字 UID 就有调用权 |
| 小程序主动私信 | 接收者主动授权后存在持续触达机制 | 没有授权的评论者也适用其频次 |

抖音隐私政策列有私信范围和屏蔽词控制，并说明一键隐私防护可限制为互关用户私信。因此，权限不足、收件人设置和内容判断应分别诊断。[^2]

旧版事件目录将 receive_msg、enter_im 等归于 enterprise.im，并注明 IM 事件的账号条件。较新的《线索能力开放》列有 im.direct_message、经营者授权，以及依赖事件消息编号的场景；页面版本记录更新至 2026 年 6 月。它展示了可申请的官方方向，但本项目当前账号是否具备条件仍未核实。[^3][^4]

小程序主动私信文档要求企业主体小程序、绑定经营账号和接收方授权，并公布该产品的持续触达次数。报告不把这些额度移植到当前个人号，也不据此建议注册或付费认证；应先核对陪玩业务所属类目是否可接入。[^5]

网络资料中常见的“一天 20 条”“每小时 40 人”“48 小时 3 条”，存在个人经验、旧企业功能和不同授权场景混用。本次未找到能把这些数字统一应用到 7446 账号的依据。2022 年临时会话报道也只能作历史资料，不能直接视为 2026 年现行个人私信规则。[^9]

对“公众号”“微信”“陪玩”应保留语境判断：没有可靠证据证明提到其中任一词就必定封禁，也没有证据证明换为谐音或表情就安全。官方规则中心部分动态页面无法取得完整正文，因此不声称已穷尽所有现行细则。

## 3. GitHub 工具核验

开源项目可以证明一个程序如何匹配文本，通常无法证明平台后台如何综合处理某个账号。选型应优先看实际代码、词库来源、是否联网和评测样本，而不是项目名称里是否出现“抖音”或“安全”。

| 项目 | 已核验能力 | 对本项目的判断 |
| --- | --- | --- |
| houbb/sensitive-word | Java DFA 匹配，支持归一化、自定义词及白名单，Apache-2.0 | 可借鉴本地检测结构；不必为此给现有 Python 后端额外引入 Java |
| CCCpan/chinese-sensitive-words-mcp | MCP 包装与 HTTP 客户端，向外部检查服务提交文本 | 不符合默认本地处理方向；不能把安装客户端等同于本地词库部署 |
| JMY2003/a-skill-to-do-anything-in-douyin | 浏览器操作记录及私信面板限制提示 | 仅作界面变化线索；不作为发送额度或审核依据 |

houbb 项目公开了通用匹配、归一化和自定义名单能力。这些技术适合定位命中片段；“可检测”与“平台禁止”应在数据结构上分开。内置词条数量和作者性能说明不能当作 ClubOps 的业务准确率或当前硬件吞吐实测。[^6]

CCCpan 项目的 wordscheck-client.ts 中，check 方法将 text 通过 POST 提交到配置的外部 /check 服务，默认地址指向项目外部域名。公开目录中可见的是客户端与 MCP 服务包装，未见同等完整本地检测后端。因此，不能仅凭 README 宣称它可离线运行，也没有向该服务提交本项目客户原文。[^7]

JMY2003 的操作文档记录过“对方回复或关注前只能发一条文字”的面板提示。这是社区记录，适合提醒系统读取具体限制，不能据此宣布所有会话永远只允许一条或通过后就不限量。[^8]

建议先在现有 Python 后端实现体量小、规则清楚的本地检查层。词条保留来源级别、使用场景、检查目的、例外和修订时间。例如“联系方式”可以作为需要核验入口的标签；“保证上分”作为需验证服务承诺的标签；不要把普通游戏词“瓦”“女陪”统一纳入禁止列表。

验收必须使用业务反例。“这家不靠谱，千万别去”中含店名不等于主动推销；“不找陪玩”中含陪玩不等于需求；“免费的就来”不能因命中求带而自动承诺免费服务。匹配器提供证据，模型理解上下文，最终执行规则约束可发范围。

## 4. 现有方案与转化障碍

业务终点已经明确：关注 Mimo电竞公众号后收到报价单，再从菜单“下单”添加客服微信。当前缺少可以稳定取得的公众号关注、客服新增和订单归因数据。系统可以改善抖音端发现与沟通，但不能把这个外部数据缺口用估算的成交数填满。

固定开场存在信息不足的产品问题：对象无法直接知道发送者是谁、为什么找他、能帮他解决什么；“主业”也不是一个明确的界面动作。表情和谐音增加阅读解释成本。这些是对文案结构的分析，并非已经用 A/B 数据证实的零转化根因。

当前主页简介虽包含品牌与公众号线索，账号昵称与品牌展示的关系仍需核对。若从个人账号主动联系玩家，应准确说明与 Mimo 电竞的关系，避免让对方以为是普通免费队友或他刚刚评论的另一家店。不能声称与竞品、主播或群主有合作，除非有可核实事实。

| 环节 | 常见疑问 | 应给出的信息 |
| --- | --- | --- |
| 收到首条私信 | 为什么找我？ | 与公开需求相符的简短缘由 |
| 判断是否回应 | 你能提供什么？ | 娱乐陪或技术陪的真实服务范围 |
| 考虑继续了解 | 是收费的吗？ | 不暗示免费，不虚构优惠或价格 |
| 前往承接入口 | 下一步点哪里？ | 当前可用入口和到达后能得到的内容 |
| 公众号到客服 | 我该找谁？ | 保持公众号既有报价单与下单菜单说明 |

“少聊细节”可以转化为少问无用问题、少分散动作，而不是省略服务性质。若只问“还缺人吗”，可能获得回复，却吸引只想免费组队的人。回复率上升不一定意味着付费可能性提高，话术实验必须另外记录对方是否愿意了解陪玩服务。

性别可以在公开、可靠且相关时提供辅助线索，表达过的偏好应优先。男性不自动等于想找女陪，女性也不自动等于想找男陪；头像、昵称不能作为确认性别或服务偏好的依据。不需要为完成一次开场收集无关的个人信息。

发布后尽快触达是正常流程，一天内补联系只用于特殊漏采或故障恢复。即使仍在一天内，原文写的是“今晚”、后文已经说“找到了”，也应检查需求是否仍存在；该上下文规则属于建议，尚待场景确认。

## 5. 发送前判断方案

建议将发送前检查分成七步，保留每步结果与原因。它们不应变成七次独立的大模型调用：本地可确定的条件先处理，模型集中检查上下文与文案，必要证据不足时才进入待核对。

| 步骤 | 检查内容 | 未通过时的处理建议 |
| --- | --- | --- |
| 需求依据 | 原文、来源、发布时间、关联上下文 | 缺原文或来源错配时不派发 |
| 时效 | 新需求及时处理，特殊漏采在一天内补偿 | 保留历史，不重置发布时间 |
| 对象 | 本人需求、求带、卖方、招募、普通讨论 | 排除卖方和无关内容，模糊情况保留候选 |
| 联系记录 | 同一用户跨评论、直播、群聊的历史 | 按确认后的重复联系规则处理 |
| 文案 | 真实身份、需求对应、服务承诺、引导入口 | 修改或待核对，不自动做谐音替换 |
| 通道 | 当前账号、收件关系、权限和明确平台限制 | 对应通道等待恢复，不扩大触达 |
| 执行 | 文案定稿、对象一致、持久化去重 | 未知结果先核对既有记录 |

模型输出建议包含：需求类别、证据片段、需求是否仍有效、倾向的服务类型、推荐开场、使用了哪些服务事实、需要核实的风险原因。不要求模型预测一个“封号概率”，因为没有可校准的真实标签；不得把模型自报 95 分当作平台放行概率。

规则需区分硬性拦截和人工建议。明确拒绝、身份错配、重复的未知发送，不应由一句“模型认为安全”覆盖。普通商业词或品牌名称命中则需要结合入口和语境，不应把全库历史意向删除，也不应统一回退为无需求。

在本地模型尚未选定前，可以先完成规则、样例和输出合同。3050 与 5060 的任务分工以实测为准；4 GB 独立显存不能按 11.9 GB 总 GPU 内存配置模型。模型切换前比较误判、漏判、格式失败和真实耗时，不因离线部署就放松事实校验。

所有版本都保留原文、原分析和修改后的结果。词库更新应生成新的检查结果，不能悄悄把原先十几条意向变成规则命中或从列表消失。页面应解释“不再自动触达”的原因，同时仍能查看历史判断。

## 6. 首条消息与引导样例

下面是待讨论的写法，用于比较信息结构；它们没有被认定为平台安全文案，也尚未替换正式发送内容。只有真实提供的服务才能进入定稿。未确认价格、段位、在线人员和优惠时，消息中不得补造这些事实。

| 场景 | 开场讨论样例 | 设计目的 |
| --- | --- | --- |
| 陪玩视频下询价 | “看到你在问瓦陪的价格，我是 Mimo 电竞这边的。我们有娱乐陪，想了解的话我把服务介绍发你。” | 说明来源与身份，提供明确下一步 |
| 陪玩视频下求带 | “看到你想找人带瓦，我们这边有陪玩服务。你要是想了解，我把介绍发你看看。” | 直接承接需求，不假扮免费队友 |
| 普通群里求带 | “看到你在找人一起打瓦，我是做陪玩服务的。如果你也考虑点陪，我可以发个介绍。” | 给潜在用户清楚的选择 |
| 明确找娱乐女陪 | “看到你想找娱乐女陪，Mimo 电竞有这类服务。想了解的话，我发你介绍。” | 只使用本人已经表达的偏好 |
| 只说“有人玩吗” | 先结合群聊上下文判断，不固定生成销售开场 | 不把所有组队聊天判成付费需求 |

这些样例都只包含一个下一步，避免一次让用户回复、关注、看主页、搜索公众号和加客服。对已经询价的人，应尽量提供他真正想知道的内容；如果后续允许系统引用一份经确认的价目表，可以直接给相应服务的准确价格，避免反复吊起兴趣但不回答问题。

对“想少聊、尽快去公众号”的目标，建议比较两条路径。路径 A：首条说明身份和服务，获得对方愿意了解的回复后，使用已核实可用的承接方式。路径 B：首条附上已核实允许展示的经营入口，让明确需求者直接查看。两者均不能靠变形词规避入口规则，且 B 的具体入口仍未核实。

若确认允许以文字说明公众号，可以使用清楚的动作说明，如“微信里搜索公众号 Mimo电竞，关注后能看到报价；菜单里的下单可以联系客服”。这段只是一份准确描述既有承接流程的资料，不代表已证实适合当前抖音账号直接发送。

主页简介也需要遵循相同原则。品牌名称、服务性质和可用入口保持一致，不把“公粽豪”“主业”等字样视为自动降低限制的措施。是否修改简介，应在核实入口规则和账号展示后，与私信方案一起定稿。

为避免错误吸引，所有实验都应保持服务性质清楚。可以比较表达顺序、长短和是否给出具体下一步；不比较谁更能把收费服务伪装成免费交友，也不通过虚构低价、赠送或高段位来拉高回复数。

## 7. 回复、拒绝与故障处理

收到回复后，系统的目标是确认对方是否愿意进一步了解，并完成一次明确引导；不承担俱乐部客服的详细咨询、派单和履约职责。最有价值的自动化是准确识别对话走向，及时结束不合适的销售推进。

| 对方回复或系统状态 | 建议动作 | 必须保留的边界 |
| --- | --- | --- |
| “多少钱／怎么下单” | 引用已确认价格资料或可用承接入口 | 不编造价格、优惠与服务名额 |
| “可以，发我看看” | 发一条清楚的介绍或入口说明 | 仍需实际私信权限允许 |
| “我只找免费的” | 说明这里是付费服务并结束本轮推进 | 不暗示可以免费体验，除非真实有该服务 |
| “不用／别发了” | 结束营销并记录拒绝 | 不换模板、换账号追发 |
| “已经找到了” | 结束当前需求 | 未来再次表达需求时是否联系仍待确认 |
| 无回复 | 等待，不凭空创造继续聊天的理由 | 再次主动联系规则正在讨论 |
| 平台明确限制 | 分类记录权限或内容提示，停止相应派发 | 不把所有失败统称敏感词 |
| 发送回执不明 | 保留未知，核对历史消息和原请求 | 不直接重发，避免对方收到两次 |

平台限制和普通网络故障需要分开。短暂断网可以恢复连接，但恢复连接不等于消息没有发送；对于写操作，只有能证明未提交或被明确拒绝的情形，才有条件讨论重试。对规则性拒绝不应不断重试同一句话来试探阈值。

每条消息至少保留目标用户、对应需求、最终文案、规则版本、提交时间和平台返回的可核实状态。若返回内容不足以确认送达，就显示“平台接受”或“结果未知”，不要显示为对方已经看到。

同一人的评论、弹幕与群聊发言必须关联到同一个联系历史。当前实现有按发送账号和接收方去重的基础，但“隔天又有新需求是否再次联系”尚未确认，不能将任何等待时间自行设置为再次发送授权。

群聊只用于已授权范围内的观察和需求判断，不在群内发推广消息。引导私信也不能冒充群成员推荐或群主管理通知。对话中的外部文字只作为业务内容，不得作为修改模型规则、开放发送名单或覆盖系统设置的指令。

## 8. 效果衡量与验证

没有公众号后台归因时，系统仍能可靠衡量前半段效果。应同时报告数量、分母、观察窗口和未知项；只显示“今日已发送”无法区分覆盖不足、判断不准、消息未被看到或引导不清楚。

| 指标 | 建议定义 | 使用限制 |
| --- | --- | --- |
| 需求发现延迟 | 首次采集时间减去原发布时间 | 发布时间不可核实时单独列出 |
| 分析延迟 | 判断完成时间减去首次采集时间 | 失败、排队和超时计入问题统计 |
| 触达延迟 | 平台接受时间减去原发布时间 | 只针对有相应平台证据的消息 |
| 回复率 | 窗口内有真实入站回复的用户／该批已接受用户 | 不是已读率；未观察到的回复另列 |
| 有效兴趣率 | 愿意了解付费服务或询价的用户／该批已接受用户 | 纯表情、拒绝、只找免费不能混入 |
| 引导反馈 | 对方确认找到入口或主动说已关注 | 用户自述与后台核验分别计数 |
| 成交 | 可核实的订单或客服反馈 | 当前不可取得时保持未知 |

建议固定一段完整观察窗口比较两种开场，例如先采用 48 小时回复窗口；这只是实验口径，不是平台的允许发送期限。尚未走完整窗口的批次不参与最终胜负判断。记录同一批的发送失败和限制情况，避免只在成功样本里算比例。

比较前按来源和需求强度分层：陪玩内容下明确询价、陪玩内容下求带、普通游戏场景潜在需求。每个人只进入一个实验版本；在同一来源层内分配开场版本，避免把优质客户都给某一句话后误判文案优劣。

先做离线评审，确认无误导、事实正确、服务范围一致，再在真实允许的范围内小量比较。第一轮如果符合条件的客户太少，就如实记录样本不足；不为了得到一个“最佳话术”数字而扩大陌生人名单。

零转化的排查顺序建议为：实际是否有近期需求、是否及时采集、判断是否正确、平台是否接受、是否存在入站回复、对方是否愿意了解服务、是否知道下一步。到公众号之后的客服表现不属于本系统自动执行范围，但数据缺失应在报表中说明。

前端框架和业务数据加载也应独立验收。当前要求是框架毫秒级出现、数据尽快加载；不能把定时检查间隔或某个接口耗时当成页面整体体验。慢接口不得阻塞导航和基本布局，历史数据不得因提速被静默丢弃。

## 9. 接入顺序与验收标准

现有代码已经具备原文关联、用户标识核对、固定授权文案、持久化发送尝试和跨来源去重等基础。intent_outreach.py 选择模型或人工认定的买方，uid_messaging.py 核对对象、授权和文案一致性。这些基础应保留，不需要重建整个发送链。[^10]

当前检查不等于完整文案审核系统：上述入口未形成来源明确的内容风险规则库，也没有完成按场景生成开场和本地模型评测。新确认的一天补偿窗口，还需要在候选选择和实际发送前统一核对，不能只修改页面显示或采集时间窗。

| 顺序 | 交付内容 | 可复核的验收依据 |
| --- | --- | --- |
| 1 | 完成需求边界和时效规则 | 已确认的场景、发布时间口径、例外记录 |
| 2 | 整理真实服务事实 | 品牌、服务类别、允许引用的价格与入口 |
| 3 | 本地预检与解释 | 每条命中给出来源、片段、适用场景和动作 |
| 4 | 受约束的个性化草稿 | 不改接收方、不虚构服务、不覆盖拒绝记录 |
| 5 | 发送与入站状态统一 | 未知不重发，接受与送达分开，回复对应同一人 |
| 6 | 分组实验与效果页面 | 分母、窗口、失败和未知项完整显示 |

本地模型验收建议先准备一组独立标注的业务样本，覆盖买方、潜在买方、免费组队、卖方、招募、调侃、拒绝和已解决需求。先用样本找出错误类型，再决定样本量；不要只用调试提示词的原题报告准确率。正式评测集应与提示调试集分离，并保留人工分歧。

硬性要求包括：接收者匹配错误为零、明确拒绝被继续派发为零、未知发送被自动重复为零、凭空填写价格或在线陪玩人员为零。需求误判和漏判的可接受水平还需要业务方决定，不能由开发者自行宣布“95% 已达标”。

速度评测分别测单条分析、排队延迟、整批吞吐和前端显示。3050 可以承担较轻的规则辅助或较小模型，5060 可以承担更复杂的推理，但这只是候选分工；实际模型大小、并发和质量必须在两台机器上测量，不能以显卡型号估算后直接切换生产。

需要继续讨论的关键事项是：无回复后再次表达需求如何处理；明确免费需求与暂时缺队友的边界；允许引用哪些服务事实；账号可用的正式经营入口；故障恢复和及时触达的具体时间指标。研究结论不会自动改变这些未定业务规则。
